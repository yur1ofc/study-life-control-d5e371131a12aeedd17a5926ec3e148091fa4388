============================================================ 1. O QUE É
O SLCAMPUS ============================================================

Nome: SLCampus Ecossistema/marca: SL Produto futuro relacionado: SLGym

O SLCampus é uma plataforma web de organização acadêmica e inteligência
de estudos.

Ele não deve ser entendido como:

-   simples calendário;
-   lista de tarefas;
-   calculadora de notas;
-   cronômetro;
-   bloco de anotações.

A ideia do produto é integrar os dados acadêmicos e comportamentais do
aluno para transformar dados em decisões.

Filosofia central:

DADOS → CONTEXTO → ANÁLISE → PRIORIDADE → PLANO → EXECUÇÃO → EVIDÊNCIA
DE APRENDIZAGEM → ADAPTAÇÃO

Exemplo:

Uma nota baixa não deve existir somente na tela de notas.

Ela pode influenciar:

-   prioridade;
-   Mentor IA;
-   plano de estudos;
-   dificuldade;
-   revisão;
-   dashboard;
-   recomendações;
-   histórico;
-   previsão matemática de média.

Da mesma forma, uma sessão de estudo não é apenas histórico.

Ela pode alimentar:

-   horas estudadas;
-   consistência;
-   dificuldade;
-   aprendizagem;
-   revisão;
-   mapa de aprendizagem;
-   adaptação;
-   prioridade futura.

============================================================ 6. SEMESTRE
ATUAL VS HISTÓRICO
============================================================

Esse é um dos princípios mais importantes do projeto.

SEMESTRE ATUAL:

representa o que o aluno está cursando agora.

HISTÓRICO:

representa períodos anteriores.

Se o aluno reprovou em Física em 2025.1 e está cursando Física novamente
em 2026.2:

-   2025.1 permanece histórico;
-   2026.2 é a tentativa atual;
-   a nota atual domina a análise atual;
-   a reprovação anterior pode ser usada como contexto de dificuldade;
-   a reprovação anterior não pode substituir a nota atual;
-   o sistema não deve tratar o aluno como permanentemente ruim naquela
    disciplina.

Consultas atuais não podem misturar silenciosamente dados antigos.

Exemplo:

“Quais provas tenho esta semana?”

Deve consultar o semestre atual.

“Já reprovei Física?”

Pode consultar o histórico.

O histórico pode conter:

-   períodos;
-   disciplinas;
-   códigos;
-   carga horária;
-   notas;
-   frequência;
-   situação;
-   aprovação;
-   reprovação;
-   matrícula atual;
-   componentes pendentes.

Situações possíveis incluem:

APR REP MATR REC CANC TRANC INCORP etc.

Existe parser determinístico para formatos conhecidos e IA para
documentos que precisam de interpretação.

Fluxo ideal:

SIGAA PDF → pdf-parse → parser SIGAA → períodos → disciplinas → situação
→ notas → frequência → identificação do período atual → histórico.

Não usar IA desnecessariamente quando um parser determinístico consegue
resolver.

============================================================ 8.
CURRÍCULO / GRADE CURRICULAR
============================================================

O SLCampus possui catálogo/importação de currículo.

Pode trabalhar com:

-   carga horária;
-   créditos;
-   obrigatórias/eletivas;

Currículo e histórico são entidades diferentes.

Currículo: “O que faz parte do curso?”

Histórico: “O que este aluno já cursou?”

Os dois podem ser cruzados para descobrir:

-   concluídas;
-   em andamento;
-   pendentes;
-   próximos componentes;
-   reprovações;
-   progresso.

Também existe sincronização entre matérias cadastradas e currículo.

============================================================ 10. NOTAS E
PREVISÃO ============================================================

O SLCampus possui cálculo de notas.

Avaliações podem possuir:

-   valor;
-   peso;
-   data;
-   contexto;
-   disciplina.

O sistema calcula:

-   média atual;
-   peso acumulado;
-   peso restante;
-   média necessária;
-   máximo possível;
-   situação objetiva.

Exemplo:

Se o aluno possui 5,5 em uma avaliação que representa 20% e deseja média
7,0, o sistema deve calcular matematicamente quanto precisa obter no
restante.

Não inventar probabilidades como:

“você tem 73% de chance de passar”.

A inteligência deve trabalhar com dados objetivos.

Também existe importação de notas com IA e estrutura de avaliações.

ATENÇÃO: Esse fluxo precisa de testes reais com diferentes combinações
de pesos, avaliações e histórico para garantir que nenhum caso limite
quebre o cálculo.

-   overtime;

-   break.

O sistema pode:

IMPORTANTE: Tempo de foco precisa continuar correto mesmo se a aba

segundo como fonte da verdade.

============================================================ 15.
EVIDÊNCIA DE APRENDIZAGEM
============================================================

Depois de uma sessão o aluno pode registrar algo como:

1.  Consigo explicar sem olhar.
2.  Consigo resolver exercícios.
3.  Ainda tenho dúvidas.
4.  Preciso revisar.

Isso alimenta o motor de aprendizagem.

Respostas de dúvida/revisão devem aumentar a necessidade de atenção.

Domínio pode permitir espaçamento maior.

O sistema deve diferenciar:

-   exposição;
-   compreensão;
-   recuperação;
-   aplicação;
-   necessidade de revisão.

============================================================ 19.
ADAPTIVE LEARNING ENGINE
============================================================

Existe motor adaptativo.

Ele tenta separar:

CAPACIDADE: quanto o aluno consegue estudar.

EFICIÊNCIA: quanto o aluno consegue aprender com o tempo investido.

Considera:

-   minutos disponíveis;
-   sessões;
-   carga;
-   execução histórica;
-   desempenho;
-   retenção;
-   revisões;
-   dúvidas.

O sistema não deve simplesmente recomendar cada vez mais horas quando o
aluno está mal.

Pode ser necessário identificar:

-   falta de tempo;
-   falta de consistência;
-   método ruim;
-   conteúdo difícil;
-   excesso de carga;
-   baixa retenção.

Também existem preferências de horário e duração de sessão.

============================================================ 20.
PRIORIDADE ACADÊMICA
============================================================

Existe conceito de prioridade determinística.

Ela não é probabilidade de aprovação.

Pode combinar:

-   proximidade de prova;
-   nota atual;
-   peso restante;
-   média necessária;
-   dificuldade;
-   atraso;
-   tarefas;
-   dúvidas;
-   revisões;
-   tempo desde estudo;
-   frequência;
-   carga;
-   histórico;

-   tendência.

Exemplo:

prioridade menor.

A prioridade deve ser explicável.

============================================================ 21.
DECISION ENGINE
============================================================

O produto deve evoluir de “mostrar dados” para “tomar decisões
explicáveis”.

Exemplo:

Dados:

-   prova sexta;
-   média atual 5,2;
-   precisa de 7,8;
-   assunto X com dúvidas;
-   assunto Y dominado;
-   3h disponíveis.

Decisão:

-   priorizar disciplina;
-   priorizar assunto X;
-   praticar exercícios;
-   reservar tempo;
-   deixar Y para revisão posterior.

Toda recomendação importante deve ter motivo compreensível.

============================================================ 46.
PRINCIPAIS PONTOS DE ATENÇÃO ARQUITETURAIS
============================================================

1.  PROJETO GRANDE EM JS PURO

app.js e views.js concentram muita responsabilidade.

Existe documentação anterior indicando necessidade de refatoração.

Não fazer uma reescrita total de uma vez.

Preferir migração incremental.

2.  MUITOS PATCHES/MÓDULOS

O projeto possui muitos arquivos que fazem patches sobre outros
arquivos.

Antes de alterar uma função, procurar:

-   quem chama;
-   quem sobrescreve;
-   quem faz patch;
-   quem depende dela;
-   ordem dos scripts.

3.  FIRESTORE / CRESCIMENTO DE DADOS

Há muitos arrays no documento do usuário.

Existem limites nas rules, mas isso não elimina o limite estrutural de
tamanho do documento do Firestore.

A arquitetura futura já prevê:

users/{uid}/semesters/{semesterId}

Isso deve ser priorizado antes de o produto crescer muito.

4.  NOMES LEGADOS DE GEMINI

Há muitos nomes históricos “gemini”.

Não renomear indiscriminadamente.

Mapear dependências primeiro.

5.  CRON

O cron diário não é suficiente para inteligência em tempo real.

6.  SERVICE WORKER

Sempre atualizar cache version quando alterar assets críticos.

7.  IA

Nunca confiar cegamente na resposta da IA.

Importações precisam de validação.

8.  HISTÓRICO

Não permitir que períodos antigos contaminem consultas atuais.

9.  NOTAS

Nunca produzir probabilidades inventadas.

10. DELETE ACCOUNT

Testar limpeza de dados relacionados.

============================================================ 50. VISÃO
DE PRODUTO A LONGO PRAZO
============================================================

O objetivo final do SLCampus é ser um “sistema operacional acadêmico
pessoal”.

O ciclo deve ser:

O aluno cadastra/importa seus dados → SLCampus entende o contexto →
identifica prioridades → cria plano → aluno executa → sistema registra o
que realmente aconteceu → aluno fornece evidência de aprendizagem →
sistema atualiza o mapa de aprendizagem → adapta
dificuldade/tempo/revisão → recalcula prioridades → Mentor explica →
Telegram/notificações lembram → ciclo continua.

O produto deve aprender sobre o processo de estudo sem transformar o
aluno em apenas uma coleção de notas.
